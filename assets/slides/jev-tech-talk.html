Jev

생성형 LLM과 다른 의사결정 모델

State, Primitives, Probability, Production

기준 모델: jev-1.13.0 · 기준일: 2026-09-20 발표자 david1-p 01
발표 도입: Jev를 더 작은 LLM이나 새로운 챗봇으로 소개하지 않는다. 이 발표의 질문은 “텍스트 생성 모델과 다른 출력 계약이 소프트웨어 설계를 어떻게 바꾸는가”이다.

01 · Problem framing

생성형 LLM과 Jev의 출력 목적

Generate

일반 LLM

  • 사람이 읽을 텍스트와 코드를 생성
  • 열린 답변 공간과 복합 추론에 적합
  • 구조화 출력도 생성 과정의 결과
VS
Decide

Jev / System One

  • 코드가 직접 쓸 타입이 정해진 답을 반환
  • 호출자가 답의 공간을 먼저 정의
  • 선택지별 확률과 불확실성을 노출
출처: Introduction · System One 02
핵심: 공식 문서는 LLM을 인간이 읽을 텍스트를 만드는 시스템으로, System One을 소프트웨어가 직접 사용할 결정을 만드는 시스템으로 구분한다. Jev는 답변, 코드, 추론 설명을 생성하지 않는다.

02 · System One

System One의 입력과 출력 계약

INPUT

State

문자열, JSON 객체, 텍스트 배열로 판단 대상과 근거를 제공한다.

EVALUATION

Typed questions

Choice, Score, Noul 질문을 같은 State에 대해 독립적으로 평가한다.

OUTPUT

Typed answers + probabilities

코드가 비교하고 정렬하고 임계값으로 분기할 수 있는 값을 반환한다.

choicescorenoulprobabilities

질문 간 숨은 대화 문맥을 만들지 않고, 각 질문을 같은 State에 대해 독립적으로 평가한다.

출처: System One · Primitives 03
System One의 공식 정의: State를 평가하고 typed answers와 probabilities를 반환하는 AI 모델 부류다. 질문은 병렬로 처리되며, 한 질문의 결과가 다른 질문의 숨은 문맥이 되지 않는다.

출처: State · 텍스트 입력만 지원 05
설계 원칙: 필요한 근거만 보내고, 질문에서 중첩 경로를 명시한다. Jev는 이미지, 음성, 영상을 직접 받지 않으므로 먼저 텍스트나 구조화 필드로 변환해야 한다.

05 · Official API example

공식 Choice 요청과 응답

Input · State + typed question

state = "My running shoes arrived in the wrong size.
Can I swap them for a size 10?"

questions = {
  "department": Choice(
    instructions="Which team should handle this?",
    criteria={
      "returns": "Exchanges, wrong or damaged items",
      "shipping": "Delivery status, delays, lost packages",
      "billing": "Charges, invoices, payment problems"
    }
  )
}

Output · Typed answer + uncertainty

{
  "model": "jev-1.13.0",
  "answers": {
    "department": {
      "type": "choice",
      "choice": "returns",
      "confidence": 1.0,
      "probabilities": {
        "shipping": 0.0,
        "returns": 1.0,
        "billing": 0.0
      }
    }
  },
  "usage": {"input_tokens": 328, "output_tokens": 34}
}

질문 ID department가 응답 키로 유지된다. 코드는 choice로 분기하고 probabilities와 confidence로 검토 정책을 정한다.

출처: Choice · 공식 SDK 요청 예시를 화면용으로 축약, 응답값은 원문 유지 06
읽는 순서: 왼쪽에서 State와 답의 공간을 함께 보낸다. Jev는 자유로운 문장을 생성하지 않고 오른쪽처럼 타입이 정해진 답을 돌려준다. 이 쉬운 티켓에서는 returns가 1.0이다. 실제 경계 사례에서는 분포가 여러 옵션으로 갈리고 confidence가 낮아지므로 코드가 자동 처리와 사람 검토를 나눈다.

사용법: false positive가 비싸면 yes 임계값을 높이고, true positive를 놓치는 것이 비싸면 낮춘다. 여러 속성이 동시에 참일 수 있는 다중 라벨 체크리스트에는 여러 Noul을 같은 호출에 넣는다.

10 · Uncertainty

Probability와 Confidence

[ ]
probabilities
옵션·수준 전체에 분배된 정보
0…1
confidence
분포 집중도를 요약한 스칼라

Noul은 이진 분포이므로 P(yes) 하나가 분포를 완전히 나타낸다.

해석에서 지켜야 할 경계

  • 최고 확률과 confidence는 같은 값이 아니다.
  • confidence 0.8은 개별 답의 80% 정답 보증이 아니다.
  • Calibration은 예측 집단에서 측정하는 통계적 성질이다.
  • 실제 임계값은 자체 데이터와 행동 위험으로 정한다.
출처: Confidence · System One 11
발표 포인트: 확률을 보여준다는 사실만으로 신뢰성이 보장되지 않는다. 프로젝트 데이터에서 confidence와 정확도의 관계를 측정하고, 업무 위험별로 다른 threshold를 둬야 한다.

12 · Patterns

코드 중심의 네 가지 아키텍처 패턴

01

Speculative fan-out

필요할 수 있는 독립 질문을 한 요청에 보내고 코드가 사용할 답을 고른다.

02

Confidence routing

답의 종류와 confidence를 함께 보고 자동 처리, 확인, 검토로 나눈다.

03

Composite scoring

여러 Score를 정규화하고 업무 가중치는 코드에서 결합한다.

04

Intent routing

결정론적 코드, 전문 LLM, 사람 중 적절한 처리기로 보낸다.

답은 무엇인지 알려주고, confidence는 행동할지 결정하는 두 번째 축이 된다.

출처: Patterns · Confidence-gated routing 13
주의: 공식 예시의 0.6, 0.85 같은 수치는 출발점일 뿐이다. 문서도 올바른 threshold는 도메인, 모델 성능, 오판 비용에 따라 정하라고 명시한다.

16 · Known limitations

Jev 1.13의 공식 실패 모드

코드가 더 잘하는 일

  • 수학과 숫자 정밀도
  • 개수 세기
  • 날짜·시간 비교
  • Score로 정확한 수량 보간

질문과 State의 위험

  • 문자 그대로의 해석
  • 여러 단계의 간접성
  • 무관한 정보가 많은 State
  • 적대적 콘텐츠
  • 서로 모순된 instructions와 criteria

능력의 경계

  • 상식적 구조 불변성 미보장
  • 질문과 부정 질문의 합이 1이 아닐 수 있음
  • 텍스트·코드·설명 생성 미지원

산술은 코드에, 생성은 LLM에, Jev에는 의미 판단만 맡긴다.

출처: Jev 1.13 jaggedness · 2026-09-17 검토 17
발표에서 강조: Jev는 결정론적이지 않으며 구조적 항등식도 자동 보장하지 않는다. 같은 결정을 한 가지 질문 형태로 평가하고, 합계·상호배타성·보수 관계는 코드에서 강제한다.
