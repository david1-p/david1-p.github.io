1. RAG란 무엇인가

1.1 정의

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 사전 학습된 파라메트릭 메모리(parametric memory, 모델 가중치)와 비파라메트릭 메모리(non-parametric memory, 외부 문서 인덱스)를 결합해 텍스트를 생성하는 모델이다. 원 논문에서 파라메트릭 메모리는 사전 학습된 seq2seq 모델(BART), 비파라메트릭 메모리는 신경망 검색기(neural retriever)로 접근하는 위키피디아의 밀집 벡터 인덱스(dense vector index)였다. [1]

1.2 등장 배경 — Lewis et al. 2020 (arXiv 2005.11401)

  • 논문 제목: Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks. 2020년 5월 22일 arXiv 제출, NeurIPS 2020 채택, 2021년 4월 12일 최종 개정. [1]
  • 문제의식: 대형 사전 학습 언어 모델은 파라미터 안에 사실 지식을 저장하지만, 지식에 정밀하게 접근·조작하는 능력이 제한되어 지식 집약적(knowledge-intensive) 과제에서 과제 전용 아키텍처보다 성능이 뒤처지고, 답변의 출처(provenance) 제시와 세계 지식 갱신이 미해결 과제로 남아 있었다. [1]
  • 두 가지 변형: RAG-Sequence는 생성되는 시퀀스 전체에 동일한 검색 문단을 사용하고, RAG-Token은 토큰마다 다른 문단을 참조할 수 있다. [1]
  • 결과: 세 개의 오픈 도메인 QA 벤치마크에서 SOTA를 달성했고, 생성 과제에서는 파라메트릭 전용 seq2seq 베이스라인보다 "더 구체적이고, 다양하며, 사실적인" 텍스트를 생성했다. [1]

1.3 왜 필요한가

문제 설명 출처
환각(hallucination) LLM은 자신이 담고 있는 파라메트릭 지식에만 의존하기 때문에 사실 오류를 낸다. Self-RAG 논문은 이를 "sole reliance on the parametric knowledge they encapsulate"로 인한 factual inaccuracies라고 표현한다. [23]
지식 갱신·출처 원 RAG 논문이 지적했듯 파라메트릭 모델은 지식 갱신과 출처 제시가 어렵다. 외부 인덱스는 교체·갱신이 가능하고, 검색된 문단이 곧 출처가 된다. [1]
비공개·미학습 데이터 LangChain 문서는 RAG를 "런타임에 인덱싱된 데이터에 접근하도록 LLM을 보강"하는 패턴으로 설명하며, 검색은 "질의 시점에 관련 외부 지식을 가져와" LLM의 근본적 한계를 해결한다고 설명한다. [2][3]
환각 완화 RAGAS 논문은 RAG가 LLM에 참조 텍스트 DB의 지식을 제공하여 사용자와 텍스트 DB 사이의 자연어 계층으로 동작하게 하고, 환각 위험을 줄인다고 설명한다. [33]

2. 기본 파이프라인 — Indexing / Retrieval / Generation

LangChain 공식 문서는 인덱싱을 네 단계로 정리한다: "1. 데이터 소스를 Document 객체로 로드 → 2. 큰 Document를 작은 청크로 분할 → 3. 임베딩 모델로 각 청크를 숫자 벡터로 변환 → 4. VectorStore에 청크와 임베딩을 인덱싱". [2] 그 다음 질의 시점에 Retrieval(관련 청크 검색)과 Generation(질문 + 검색 결과를 프롬프트에 넣어 LLM이 답변 생성)이 이어진다. [3]

[Load] → [Split] → [Embed] → [Store]        ← Indexing (오프라인)
[Query] → [Retrieve] → [Generate]           ← 질의 시점 (온라인)

2.1 Load — 문서 로더

  • LangChain의 시맨틱 검색 튜토리얼은 page_content와 metadata를 가진 Document 객체를 만들고, pypdf로 PDF 페이지를 추출하는 흐름을 보여준다. [4]
  • Deep Agents RAG 가이드에서는 requests로 https://docs.langchain.com/{path}.md 마크다운 페이지를 가져와 source 메타데이터를 붙인 Document를 만든다. 14개 문서 페이지에서 782개 청크가 생성되었다. [2]

2.2 Split — 청킹 전략

LangChain 텍스트 스플리터 문서는 분할 방식을 다음과 같이 분류한다. [5]

전략 설명 출처
길이 기반 (Length-based) 토큰 수 또는 문자 수로 분할해 청크 크기를 일정하게 유지 [5]
텍스트 구조 기반 (재귀 분할, RecursiveCharacterTextSplitter) 문단 → 문장 → 단어의 계층 구조를 활용, 큰 단위를 최대한 유지. "대부분의 경우에 권장" [5]
문서 구조 기반 HTML, Markdown, JSON, 코드 파일의 고유 서식을 존중해 분할 [5]
시맨틱 청킹 (Semantic chunking) 임베딩 유사도의 불연속 지점에서 분할(Chroma 연구의 KamradtSemanticChunker, ClusterSemanticChunker, LLMSemanticChunker 등) [46]

공식 문서의 재귀 분할 예시: [5]

from langchain_text_splitters import RecursiveCharacterTextSplitter

text_splitter = RecursiveCharacterTextSplitter(chunk_size=100, chunk_overlap=0)
texts = text_splitter.split_text(document)

시맨틱 검색 튜토리얼에서는 chunk_size=1000, chunk_overlap=200, add_start_index=True 설정을 사용한다. [4] Deep Agents RAG 가이드도 RecursiveCharacterTextSplitter를 "일반 텍스트에 권장되는 TextSplitter"로 소개하며 chunk_size=1000, chunk_overlap=200을 쓴다. [2]

단위 주의: RecursiveCharacterTextSplitter의 chunk_size는 기본적으로 문자 수 기준이며, 구분자 목록 ["\n\n", "\n", " ", ""]을 순서대로 시도해 문단 → 줄 → 단어를 최대한 유지한다(별도 문장 분석기가 아니다). 따라서 위의 1000자는 아래 Chroma 연구의 "200토큰"이나 OpenAI Retrieval의 "800토큰"(6.4절)과 직접 비교할 수 없다. 토큰 기준으로 맞추려면 length_function에 tokenizer를 넘기거나 TokenTextSplitter를 쓰고, 어떤 tokenizer인지 기록한다.

청크 크기는 어떻게 정하나? Chroma의 청킹 평가 연구(2024-07-03)는 RecursiveCharacterTextSplitter, TokenTextSplitter, KamradtSemanticChunker, KamradtModifiedChunker, 그리고 새로 제안한 ClusterSemanticChunker, LLMSemanticChunker를 토큰 단위 recall/precision/IoU로 비교했다. 결과적으로 "청킹 전략 선택이 검색 성능(정확도·효율)에 상당한 영향"을 주며, 200토큰·오버랩 없음 설정이 대체로 정밀도·효율이 높았고, 큰 청크는 recall은 오르지만 토큰 효율이 떨어졌다. ClusterSemanticChunker(200토큰)가 정밀도·효율 최고, LLMSemanticChunker가 recall 최고였다. [46]

청킹의 한계와 대안: 청크를 따로 임베딩하면 주변 문맥이 사라진다. 이를 해결하는 Late Chunking(3.8절)과 Contextual Retrieval(3.3절)을 참고. [27][22]

2.3 Embed — 임베딩 모델

OpenAI text-embedding-3 [7] - text-embedding-3-small(기본 1536차원)과 text-embedding-3-large(기본 3072차원). 최대 입력 8,192토큰. - 공식 가이드의 MTEB 점수: small 62.3%, large 64.6%, 구형 ada-002 61.0%. 비용 효율(pages per dollar): small 62,500, large 9,615. - dimensions 파라미터로 임베딩을 줄일 수 있으며, "MTEB에서 text-embedding-3-large를 256차원으로 줄여도 1536차원의 ada-002보다 성능이 높다".

오픈소스 모델과 MTEB/MMTEB 리더보드 - MTEB는 "임베딩과 검색 시스템을 평가하는 멀티모달 툴박스"이며, 인터랙티브 리더보드는 Hugging Face Spaces(mteb/leaderboard)에 있다. [9] - MMTEB(Massive Multilingual Text Embedding Benchmark, arXiv 2502.13595, 2025-02-19 제출, 2025-11-13 최종판)는 250개 이상 언어, 500개 이상 태스크로 확장한 벤치마크로, 명령 수행(instruction following), 장문 검색, 코드 검색 같은 새 태스크를 포함한다. 주요 발견: 5억 6천만 파라미터의 multilingual-e5-large-instruct가 공개된 더 큰 LLM 기반 모델들을 능가하는 등 작은 다국어 모델이 대형 LLM을 이기는 경우가 많다. [8] - 실무 팁: LangChain 문서는 OpenAI, Azure, Google, AWS, HuggingFace 등 여러 임베딩 공급자를 같은 인터페이스로 지원하므로 모델 교체가 쉽다. [2]

2.4 Store — 벡터 스토어

LangChain 벡터 스토어 통합 문서는 FAISS, Chroma, PGVector, Pinecone, Qdrant, Milvus, Weaviate, MongoDB Atlas, Redis, Elasticsearch 등 50개 이상의 스토어를 나열하며, 통일된 추상화 덕분에 애플리케이션 로직 수정 없이 구현체를 바꿀 수 있다. [6]

스토어 특징 출처
FAISS Meta FAIR가 개발한 "밀집 벡터의 효율적 유사도 검색·클러스터링 라이브러리". RAM에 들어가지 않는 크기의 벡터 집합도 다룸. C++ 구현 + Python 래퍼, GPU 지원 [10]
Chroma / Milvus / Pinecone / Qdrant 벡터 검색 전용 스토어. LangChain 통합 목록에 포함 (langchain_pinecone.PineconeVectorStore, langchain_qdrant.QdrantVectorStore 등) [2][6]
MongoDB Atlas / PGVector / Redis / Elasticsearch 범용 DB에 벡터 검색 기능을 얹은 형태 (MongoDB는 $vectorSearch 집계 스테이지, Postgres는 pgvector 확장 → langchain_postgres.PGVectorStore). 기존 데이터와 임베딩을 한 곳에 둘 수 있음 [2][6]
InMemoryVectorStore 학습·프로토타입용 인메모리 스토어 [2][6]

공식 문서의 기본 사용 예: [6]

from langchain_core.vectorstores import InMemoryVectorStore

vector_store = InMemoryVectorStore(embeddings)
vector_store.add_documents(documents=[doc1, doc2], ids=["id1", "id2"])
similar_docs = vector_store.similarity_search("your query here")
vector_store.similarity_search(
    "query",
    k=3,
    filter=lambda doc: doc.metadata.get("source") == "tweets",
)

2.5 Retrieve — 검색 방법

방법 설명 출처
Dense(밀집) 검색 DPR(Dense Passage Retrieval, 2020)은 듀얼 인코더(dual-encoder)로 질문·문단 임베딩을 학습해 "밀집 표현만으로 검색을 실용적으로 구현"할 수 있음을 보였고, 여러 오픈 도메인 QA에서 Lucene-BM25 대비 top-20 문단 정확도가 9–19%p 높았다. [11]
Sparse(희소)/BM25 키워드 기반 어휘 매칭. DPR 논문의 비교 대상이며, Anthropic의 Contextual BM25처럼 정확한 용어 매칭이 필요한 경우 밀집 검색을 보완한다. [11][22]
Hybrid(하이브리드) LangChain EnsembleRetriever는 "여러 리트리버를 앙상블하고 rank fusion을 사용"하며, weighted_reciprocal_rank() 메서드로 가중 RRF(Reciprocal Rank Fusion)를 수행한다. weights는 리트리버별 가중치(기본은 균등), c는 순위에 더하는 상수로 상위·하위 순위의 중요도 균형을 조절한다. OpenAI Retrieval API도 hybrid_search.embedding_weight/text_weight로 "RRF가 의미 임베딩 매칭과 희소 키워드 매칭을 어떻게 균형 잡을지" 제어한다. [12][45]
MMR(Maximal Marginal Relevance) "질의와의 유사도 그리고 선택된 문서 간 다양성을 함께 최적화". k(반환 수, 기본 4), fetch_k(MMR에 넘길 후보 수, 기본 20), lambda_mult(0=최대 다양성, 1=최소 다양성, 기본 0.5). [13]

2.6 Rerank — 리랭킹

  • Cross-encoder 리랭커(Cohere Rerank): query와 documents 목록을 받아 "질의와 의미적으로 가장 관련 있는 순서로" 정렬하고 문서별 관련도 점수를 반환한다. 모델 라인업은 Rerank 4.0(rerank-v4.0-pro, rerank-v4.0-fast, 단일 다국어), Rerank 3.5(rerank-v3.5), Rerank 3.0(영어/다국어 별도). 100개 이상 언어 지원. [14]
  • ColBERT(Late interaction): 질의와 문서를 BERT로 독립적으로 인코딩한 뒤 "저렴하지만 강력한 상호작용 단계"로 세밀한 유사도를 계산한다. 문서 표현을 오프라인에 미리 계산할 수 있어 기존 BERT 기반 랭킹 대비 "두 자릿수 배 빠르고, 질의당 FLOPs는 네 자릿수 배 적다". 리랭킹과 엔드투엔드 검색 모두에 사용 가능. [15]
  • 효과: Anthropic 실험에서 Contextual Retrieval에 리랭킹을 더하면 검색 실패율이 67% 감소했다(리랭킹 없이 49%). [22]
  • OpenAI Retrieval API도 ranking_options(ranker 지정, 0.0–1.0 score threshold)로 리랭킹을 제공한다. [45]

3. Advanced RAG 기법

3.1 쿼리 변환(Query Transformation)

기법 핵심 아이디어 원 출처
Multi-Query LangChain MultiQueryRetriever: "질의가 주어지면 LLM으로 여러 개의 질의를 생성하고, 각 질의로 문서를 검색한 뒤, 검색된 문서의 유일한 합집합(unique union)을 반환". [16]
HyDE (Hypothetical Document Embeddings) 명령 수행 LLM(InstructGPT)에게 질의에 대한 가상의 문서를 생성하게 한 뒤, 비지도 대조 학습 인코더(Contriever)로 그 문서를 임베딩해 실제 문서를 검색. 가상 문서는 사실 오류를 포함할 수 있지만 관련성 패턴을 포착한다. 비지도 Contriever를 크게 앞서고 fine-tuned 검색기에 필적 (2022-12-20). [17]
Step-Back Prompting 세부 사항이 담긴 질문에서 고수준 개념·제1원리를 추상화하는 "한 걸음 물러난" 질문을 먼저 던지고, 그 원리로 추론을 유도. PaLM-2L에서 MMLU Physics +7%, Chemistry +11%, TimeQA +27%, MuSiQue +7% (ICLR 2024, Google DeepMind). [18]
RAG-Fusion "여러 질의를 생성하고, 상호 순위(reciprocal rank)로 재정렬한 뒤 문서와 점수를 융합(RRF)". Infineon 사내 챗봇에서 정확하고 포괄적인 답변을 냈지만, 생성된 질의가 원 질의와 어긋나면 답이 주제를 벗어나는 한계가 관찰됨 (2024-01-31). [19]

3.2 계층적 / 부모-자식 문서 검색

  • ParentDocumentRetriever(LangChain): "작은 청크를 검색한 뒤 그 부모 문서를 반환". 정확한 임베딩을 위해서는 작은 문서가, 문맥 유지를 위해서는 긴 문서가 필요하다는 상충을 해결한다. 검색 시 작은 청크를 찾고 그 부모 ID를 조회해 큰 문서를 반환한다. [20]
  • RAPTOR(2024-01-31, Stanford): 텍스트 청크를 재귀적으로 임베딩·클러스터링·요약해 "아래에서 위로 다양한 추상화 수준의 요약 트리"를 만들고, 여러 추상화 수준에서 검색한다. GPT-4와 결합 시 QuALITY 벤치마크에서 절대 정확도 20% 향상. [21]

패키지 주의: 이 절에서 언급한 EnsembleRetriever, MultiQueryRetriever, ParentDocumentRetriever는 현재 각각 langchain_classic.retrievers.ensemble, langchain_classic.retrievers.multi_query, langchain_classic.retrievers.parent_document_retriever 모듈에 속하는 레거시 호환 API다 [12][16][20].

3.3 Contextual Retrieval (Anthropic, 2024-09-19)

  • 문제: 청크를 분리해 임베딩하면 문맥이 사라진다.
  • 방법: 청크마다 LLM(Claude)이 "이 청크를 전체 문서 안에서 위치시키는 짧고 간결한 문맥"(50–100토큰)을 생성해 청크 앞에 붙인 뒤 임베딩(Contextual Embeddings)과 BM25 인덱싱(Contextual BM25)을 수행한다. [22]
  • 결과: Contextual Embeddings 단독으로 검색 실패율 35% 감소, Contextual BM25까지 결합 시 49% 감소, 리랭킹 추가 시 67% 감소. [22]
  • 비용: 프롬프트 캐싱을 쓰면 문서 전체를 한 번만 캐시에 올리므로 문맥 생성 비용이 약 $1.02 / 100만 문서 토큰. 단, 이 수치는 "800토큰 청크, 8k 토큰 문서, 50토큰 지시문, 청크당 100토큰 문맥"이라는 가정 아래 계산된 일회성 전처리 비용이며, 2024-09 시점 모델·가격 기준이다. RAG 운영 비용 전체나 고정 단가로 쓰면 안 된다. [22]
  • RAG가 필요 없는 경우: 지식 베이스가 20만 토큰(약 500페이지) 미만이면 "RAG나 유사 기법 없이" 전체를 프롬프트에 넣을 수 있다고 안내한다. [22] 다만 이는 일반 규칙이 아니라 비교 후보다 — 모델 컨텍스트 한도, 질문·출력용 여유, 캐시 적중률, 문서 변경 빈도, 요청별 접근 권한, 비용에 따라 결론이 달라지므로 작은 코퍼스에서는 전체 삽입 + 프롬프트 캐싱을 RAG와 같은 평가셋으로 비교해 고른다.

3.4 Self-RAG (arXiv 2310.11511, 2023-10-17)

  • 단일 LM이 필요할 때(on-demand) 검색하고, 검색 문단과 자신의 생성물을 반성 토큰(reflection tokens) 으로 평가한다. [23]
  • 반성 토큰은 검색 필요 여부를 나타내는 retrieval 토큰과 생성 품질을 평가하는 critique 토큰으로 나뉜다. 토큰 생성으로 추론 시 모델을 제어(controllable)할 수 있다. [23]
  • 7B/13B Self-RAG가 오픈 도메인 QA, 추론, 사실 검증에서 ChatGPT와 Llama2-chat을 능가했고, 장문 생성의 사실성·인용 정확도가 크게 향상됐다. [23]
  • 원 논문과 LangGraph 예제의 차이: 논문의 Self-RAG는 반성 토큰을 생성하도록 학습된 모델이다. [23] LangGraph 예제 노트북은 이 아이디어를 학습 없이 별도의 LLM 채점 호출로 흉내 낸 교육용 변형으로, 설명에는 retrieve?·isREL·isSUP·isUSE 네 판단이 나오지만 그래프는 항상 START → retrieve로 시작하고(검색 여부 판단 노드 없음), 문서 관련성(grade_documents) → 생성 근거성("supported") → 응답 유용성("useful")의 세 판단만 구현한다. 근거 없음이면 재생성, 유용하지 않으면 transform_query → retrieve로 되돌아간다. [31]

3.5 Corrective RAG (CRAG, arXiv 2401.15884, 2024-01-29 / v3 2024-10-07)

  • 문제: RAG는 검색 문서의 관련성에 크게 의존하므로, 검색이 잘못되면 모델 동작이 우려된다. [24]
  • 방법: 경량 retrieval evaluator가 질의에 대한 검색 문서의 전반적 품질을 평가해 신뢰도(confidence degree) 를 반환하고, 그에 따라 다른 검색 행동을 트리거한다. 정적·제한된 코퍼스만으로는 최적 문서를 얻기 어려우므로 대규모 웹 검색으로 확장한다. 검색 문서에 decompose-then-recompose 알고리즘을 적용해 핵심 정보에 집중하고 불필요한 정보를 걸러낸다. [24]
  • "plug-and-play"로 다양한 RAG 기법과 결합 가능하며, RAG와 Self-RAG 모두에서 성능이 크게 향상됐다. [24]
  • LangGraph 예제는 CRAG를 retrieve → grade_documents → (무관 문서가 있으면) transform_query → web_search_node → generate 순서로 구현한다. 즉 질의를 먼저 재작성한 뒤 웹 검색한다. 논문의 retrieval evaluator·decompose-then-recompose는 LLM 이진 채점으로 단순화된 교육용 변형이다. [30]

3.6 Adaptive-RAG (arXiv 2403.14403, NAACL 2024)

  • 질의 복잡도 분류기(자동 수집 라벨로 학습한 작은 LM)가 질의 복잡도를 예측하고, 그에 따라 무검색 / 단일 단계 검색 / 다단계 반복 검색 전략 중 가장 적합한 것을 동적으로 선택한다. [25]
  • 반복 검색 방식과 단일 검색 방식, 무검색 방식 사이를 매끄럽게 오가며 효율과 정확도를 동시에 개선한다. [25]
  • LangGraph 예제는 질의를 웹 검색(최신 정보) 또는 벡터 스토어로 라우팅하고, 답변 품질을 평가해 기준 미달이면 교정 사이클을 도는 self-corrective RAG와 결합한다. [32]

3.7 GraphRAG (Microsoft Research, arXiv 2404.16130, 2024-04-24 / v2 2025-02-19)

  • 문제: 기존 RAG는 "이 데이터셋의 주요 주제는 무엇인가?"처럼 코퍼스 전체를 향한 전역(global) 질문에 실패한다. 이는 명시적 검색이 아니라 질의 중심 요약(query-focused summarization) 과제이기 때문이다. [26]
  • 방법: LLM으로 두 단계 그래프 인덱스를 만든다. (1) 소스 문서에서 엔티티 지식 그래프를 추출, (2) 밀접히 관련된 엔티티 그룹(커뮤니티)마다 커뮤니티 요약을 사전 생성. 질의 시 각 커뮤니티 요약이 부분 응답을 만들고, 이를 다시 요약해 최종 응답을 만든다(map-reduce). [26]
  • 결과: 약 100만 토큰 규모 데이터셋의 전역 sensemaking 질문에서 기존 RAG 베이스라인 대비 포괄성과 다양성이 크게 향상됐다. [26]

3.8 Late Chunking과 ColBERT / ColPali

  • Late Chunking(Jina AI & Weaviate, arXiv 2409.04701, 2024-09-07 / v3 2025-07-07): 긴 문맥 임베딩 모델로 문서 전체의 토큰을 먼저 임베딩하고, 청킹을 트랜스포머 이후·mean pooling 직전에 적용한다. 결과 청크 임베딩이 전체 문맥 정보를 담아 여러 검색 과제에서 우수하며, 추가 학습 없이 다양한 긴 문맥 임베딩 모델에 적용할 수 있다. [27] Jina 블로그(2024-08-22)는 이를 "각 청크 임베딩이 이전 청크들에 조건화(conditioned on)되어 더 많은 문맥을 인코딩"한다고 설명하며, 문서가 길수록 이득이 컸다고 밝힌다. [28]
  • ColBERT: 2.6절 참고. 토큰 단위 다중 벡터 표현 + late interaction. [15]
  • ColPali(ICLR 2025, arXiv 2407.01449): 텍스트 추출 대신 문서 페이지 이미지에서 Vision Language Model로 고품질 다중 벡터 임베딩을 생성하고 late interaction으로 매칭한다. 시각적 문서 검색 벤치마크 ViDoRe를 함께 제안했으며, 기존 문서 검색 파이프라인을 "크게 능가하면서 훨씬 단순하고 빠르며 엔드투엔드 학습 가능"하다. [42]

4. Agentic RAG

4.1 개념

LangChain 문서는 RAG 아키텍처를 세 가지로 구분한다. [3]

아키텍처 설명 특성
2-Step RAG 검색 → 생성이 고정 순서로 실행. "단순하고 예측 가능". FAQ·문서 봇에 적합 제어 높음, 유연성 낮음
Agentic RAG LLM 기반 에이전트가 언제·어떻게 검색할지 자율적으로 결정. "외부 지식을 가져올 수 있는 도구 하나 이상에 접근"만 하면 RAG 동작이 가능 유연성 높음, 지연 시간 가변
Hybrid RAG 두 방식을 결합. "질의 전처리, 검색 검증, 생성 후 검사" 같은 중간 단계를 도입 반복 정제·품질 관리가 필요할 때

기존 지식 베이스가 있다면 새로 만들 필요 없이 "Agentic RAG에서 에이전트의 도구로 연결"할 수 있다. [3]

4.2 LangGraph 공식 튜토리얼 — Build a custom RAG agent

공식 튜토리얼(docs.langchain.com/oss/python/langgraph/agentic-rag)은 세 단계로 진행된다: (1) 블로그 글을 가져와 청킹·인덱싱, (2) 리트리버 도구 생성, (3) 판단 로직과 피드백 루프를 가진 LangGraph 워크플로 조립. [29]

핵심 노드: [29] - 에이전트 판단 지점: 리트리버 도구를 바인딩한 모델을 호출. 문맥이 필요하면 도구를 호출하고, 아니면 검색 없이 바로 답한다. - Grade Documents: 구조화 출력(structured output) 모델이 검색 문서의 관련성을 이진 점수로 채점. 관련 있으면 답변 생성, 없으면 질문 재작성으로 라우팅. - Rewrite Question: 원 질문을 더 명확한 검색어로 재작성한 뒤 에이전트 판단 지점으로 되돌아가 재검색. - Generate Answer: 질문 + 검색 문맥으로 환각을 억제하는 프롬프트에서 답변 생성.

리트리버 도구와 조건부 엣지(공식 튜토리얼 코드): [29]

@tool
def retrieve_blog_posts(query: str) -> str:
    """Search and return information about Lilian Weng blog posts."""
    retriever = _get_retriever()
    retrieved_docs = retriever.invoke(query)
    return "\n\n".join([doc.page_content for doc in retrieved_docs])

workflow.add_conditional_edges(
    "retrieve",
    grade_documents,
)

LangGraph Graph API의 구성 요소는 State(노드가 읽고 갱신하는 공유 데이터), Node(현재 상태를 받아 한 단계를 실행하는 함수), Edge(다음 노드를 정의하는 연결, 상태에 따라 분기하는 conditional edge 포함)이다. [29]

4.3 Deep Agents의 RAG 패턴 (2026 문서)

LangChain의 Deep Agents RAG 문서는 네 가지 오케스트레이션 패턴을 제시한다. [2] 1. Skills-guided retrieval: 에이전트가 코퍼스 검색 전략을 설명하는 skill을 로드하고 그 지침대로 검색 도구를 호출. 2. Rubric-checked grounding: 에이전트가 증거를 검색해 초안을 쓰고, grader 서브에이전트가 RubricMiddleware로 근거성(groundedness)을 평가. 3. Todo-driven investigation: 조사할 페이지·질의 목록을 만들고 각각 검색한 뒤 종합. 4. Retrieve, offload, and delegate: 검색 청크를 오케스트레이터 컨텍스트가 아닌 파일시스템 백엔드(/retrieved/{batch_id}/chunk_{n}.md)에 쓰고 파일 경로만 반환, 병렬 서브에이전트가 분석. 서브에이전트가 파일을 개별로 읽어 오케스트레이터 컨텍스트를 아낀다.

4.4 LangGraph 예제 노트북 (CRAG / Self-RAG / Adaptive RAG)

langchain-ai/langgraph 저장소의 examples/rag/ 디렉터리에 langgraph_crag.ipynb, langgraph_self_rag.ipynb, langgraph_adaptive_rag.ipynb가 있다. 다만 이 디렉터리는 "순전히 보관(archival) 목적으로 유지되며 더 이상 갱신되지 않는다" 고 명시되어 있고, 최신 정보는 통합된 LangChain 문서를 보라고 안내한다. [30][31][32]

노트북 구현 흐름 출처
CRAG retrieve → grade_documents → (무관 시) transform_query → web_search_node → generate [30]
Self-RAG START → retrieve(항상 검색) → grade_documents → generate → 근거성·유용성 채점 → 실패 시 재생성 또는 transform_query → retrieve [31]
Adaptive RAG START에서 route_question이 웹 검색 또는 벡터 스토어를 선택 → 벡터 경로는 Self-RAG와 같은 채점 루프. 재작성 후에는 transform_query → retrieve로 가며 라우터를 다시 호출하지 않음(웹 검색 경로는 web_search → generate로 바로 종료) [32]

세 노트북 모두 논문 방법을 그대로 구현한 것이 아니라, 논문의 아이디어를 LangGraph 노드·조건부 엣지로 옮긴 교육용 변형이다(3.4~3.6절의 원 방법과 비교). [30][31][32]

5. RAG 평가

5.1 무엇을, 어떻게 평가하나

RAG는 검색(Retrieval) 과 생성(Generation) 두 단계로 이루어지므로 평가도 두 층으로 나눈다. Ragas 논문은 RAG 평가 차원을 "검색 시스템이 관련 있고 집중된 문맥 문단을 찾아내는 능력, LLM이 그 문단을 충실하게 활용하는 능력, 생성 자체의 품질"로 정리한다. [33] TruLens는 같은 구도를 RAG Triad라 부른다: Context Relevance(검색 청크 ↔ 질문), Groundedness(응답 ↔ 검색 문맥), Answer Relevance(응답 ↔ 질문). TruLens는 세 평가를 통과하면 "지식 베이스의 한계 안에서 환각이 없다고 검증"된 것으로 본다고 주장한다. [52] 그러나 이는 판정기가 정확하다는 전제 위의 진술이다. 세 지표는 검색 관련성·답변 근거성·질문 적합성을 점검하는 수단이지, 높은 점수가 환각의 부재나 현실 세계의 사실 정확성을 보장하지는 않는다 — 예컨대 오래된 규정을 충실히 인용한 답은 Groundedness가 높아도 현재 기준으로 틀릴 수 있고, LLM 판정기 자체가 위치·장황함·자기 선호 편향과 제한된 추론 능력을 보인다는 연구가 있다(GPT-4 판정기와 사람의 일치율은 약 80%로, 사람끼리의 일치율과 같은 수준). 

질문 ──(Context Relevance / Context Precision·Recall)──▶ 검색 문맥
  │                                                        │
  │ (Answer Relevance / Response Relevancy)     (Groundedness / Faithfulness)
  ▼                                                        ▼
응답 ◀────────────────────────────────────────────────────┘
        + 참조 답안이 있으면: Correctness / Factual Correctness

두 가지 축을 더 구분해야 한다.

축 구분 예
정답 필요 여부 참조 기반(reference-based) — 정답 문서·정답 답안이 필요 / 참조 없음(reference-free) — 질문·문맥·응답만으로 계산 Context Recall은 참조 필요 [48], Faithfulness·Response Relevancy는 참조 불필요 [35][49]
채점 방식 결정적 계산(순위 지표, ID 매칭, 문자열 유사도) / LLM-as-judge(LLM이 주장 단위로 판정) ir-measures의 P/R/nDCG [51] vs Ragas의 LLM 기반 지표 [34]

5.2 검색 평가 — 순위 지표 (IR metrics)

검색기는 "관련 문서를 찾았는가"(recall 계열)와 "위에 올렸는가"(순위 계열)로 평가한다. 정의는 ir-measures 문서 기준. [51]

지표 정의 순위 고려 언제 쓰나
Precision@k 상위 k개 중 관련 문서 비율 ✗ 프롬프트에 넣는 k개가 얼마나 깨끗한가 (노이즈 유입)
Recall@k 전체 관련 문서 중 상위 k개 안에 들어온 비율 ✗ 필요한 정보가 빠지지 않았는가
F1@k Precision과 Recall의 조화평균 ✗ 둘의 균형
Hit Rate@k (Success) 상위 k개에 관련 문서가 하나라도 있으면 1, 없으면 0. "일부에서 Recall@k라고 부르기도 하지만 TREC 관례는 구분한다" ✗ 정답 청크가 1개인 QA에서 가장 단순한 지표
MRR 첫 번째 관련 문서 순위의 역수(1/rank)를 질의 전체에서 평균 ○ 첫 번째 관련 문서를 얼마나 빠르게 찾는지 평가. 1에 가까울수록 좋은 성능(첫 관련 문서가 1위)
MAP 관련 문서가 나타날 때마다 그 지점의 Precision을 구해 평균(AP)하고, 질의 전체에서 다시 평균 ○ 여러 쿼리에 대해 평균 정밀도를 계산해 검색 결과의 정밀도를 평가. 관련 문서가 여러 개일 때 전체 순위 품질
nDCG@k 순위가 낮을수록 할인(discount)한 누적 이득을 이상적 순위의 값으로 정규화. "가장 높은 등급의 문서를 순위 맨 위에 두는 시스템"이 높은 점수 ○ 문서의 순서에 따른 관련성을 평가. 1에 가까울수록 이상적인 검색 결과(이상적 순위와 동일). 관련도가 등급(0/1/2…)일 때. MTEB/BEIR 검색 태스크의 표준
R-Precision 관련 문서 수 R 위치에서의 Precision (= 그 위치의 Recall) ✗ k를 정하기 어려울 때

손계산 예시 (rag_metrics.py로 검증). 5개를 검색했고 순서는 d1 d2 d3 d4 d5, 실제 관련 문서는 d2, d4, d7 (d7은 못 찾음).

관련 여부:  d1=0  d2=1  d3=0  d4=1  d5=0          전체 관련 문서 수 = 3

Precision@5 = 2/5 = 0.40
Recall@5    = 2/3 = 0.67
F1@5        = 2·0.40·0.67 / (0.40+0.67) = 0.50
Hit Rate@5  = 1
RR          = 1/2 = 0.50                      (첫 관련 문서 d2가 2위)
AP          = (P@2 + P@4) / 3 = (0.5 + 0.5) / 3 = 0.33   (분모: 전체 관련 문서 3, 못 찾은 d7이 감점)
DCG@5       = 1/log2(3) + 1/log2(5) = 0.631 + 0.431 = 1.062
IDCG@5      = 1/log2(2) + 1/log2(3) + 1/log2(4) = 1 + 0.631 + 0.5 = 2.131
nDCG@5      = 1.062 / 2.131 = 0.50

읽는 법: Recall은 "3개 중 2개 찾음"만 말하고, MRR·MAP·nDCG는 "찾은 것이 2·4위라 아쉽다"까지 말한다. 같은 결과를 d2 d4 d1 d3 d5로 재정렬(리랭킹)하면 Recall@5는 그대로지만 RR=1, AP=0.67, nDCG=0.77로 오른다.

단, "같은 문서 집합 전체에 대한 Recall은 재정렬로 변하지 않는다"는 것이지 리랭커가 Recall에 영향이 없다는 뜻이 아니다. 실무에서는 후보 N개(예: 150개)를 리랭킹한 뒤 상위 k개만 프롬프트에 넣으므로 [22], 최종 선택 범위의 Recall@k·Precision@k도 함께 바뀐다. 위 예시에서도 최종 선택을 상위 2개로 잡으면 Recall@2가 1/3 → 2/3으로 오른다. 그리고 순위 지표 상승만으로 RAG 전체가 나아졌다고 판단하지 말고, 답변 품질(5.4절)과 지연 시간·비용도 같이 본다.

관련 문서 라벨은 어디서 오나? 세 가지 방법이 있다. (1) 사람이 질의별로 관련 문서를 표시(TREC 방식) [51], (2) 합성 테스트셋 — Ragas는 문서로 지식 그래프를 만들고 노드에서 질문·참조 문맥·참조 답안을 함께 생성한다 [55], (3) 참조 답안만 있을 때는 Ragas의 LLM 기반 Context Recall처럼 "참조 답안의 주장이 검색 문맥에서 지지되는가"로 우회한다 [48].

공개 벤치마크: BEIR(NeurIPS 2021)는 18개 데이터셋·다양한 도메인의 zero-shot 검색 벤치마크로, BM25가 강건한 베이스라인이고 리랭킹·late interaction 모델이 평균 성능은 가장 좋지만 계산 비용이 크며, dense/sparse 모델은 효율적이지만 일반화가 약하다는 결과를 냈다. [53] 임베딩 모델 선택에는 MTEB/MMTEB(2.3절)를 본다. [8][9]

5.3 검색 평가 — Ragas 문맥 지표

순위 지표는 "관련 문서 ID"가 필요하다. Ragas는 ID가 없어도 LLM으로 관련성을 판정하는 변형을 제공한다.

지표 정의 필요한 입력 출처
Context Precision "검색기가 관련 청크를 무관한 청크보다 위에 올리는 능력". Context Precision@K = Σ_{k=1..K} (Precision@k × v_k) / (top-K 안의 관련 항목 수), v_k∈{0,1}는 k번째 청크의 관련 여부 LLM 판정: LLMContextPrecisionWithReference(참조 답안 대비) / LLMContextPrecisionWithoutReference(생성 응답 대비). 비LLM: NonLLMContextPrecisionWithReference(Levenshtein 등 문자열 유사도), ID 기반: 검색 ID ∩ 참조 ID / 검색 ID 수 [47]
Context Recall "관련 문서(정보 조각) 중 얼마나 성공적으로 검색됐는가". LLM 기반: 참조 답안을 주장으로 분해해 지지되는 주장 수 / 참조 주장 수. 비LLM: 검색된 관련 문맥 수 / 참조 문맥 수. ID 기반: 검색된 참조 ID 수 / 참조 ID 수 LLM: user_input, retrieved_contexts, reference. 비LLM: retrieved_contexts, reference_contexts [48]

주의: Ragas Context Precision@K는 위 예시의 AP와 식이 거의 같지만 분모가 "top-K 안의 관련 수" 라서 못 찾은 문서를 감점하지 않는다(예시에서 AP=0.33, Context Precision=0.50). 누락은 Context Recall이 잡는다. [47][48]

5.4 생성 평가 — 충실성·관련성·정확성

지표 정의 참조 필요 출처
Faithfulness "응답이 검색 문맥과 얼마나 사실적으로 일관되는가". 응답의 주장(claim)을 추출해 각각 문맥에서 추론 가능한지 확인, 지지되는 주장 수 / 전체 주장 수 (0–1) ✗ [35]
Response Relevancy (Answer Relevancy) 응답으로부터 인공 질문을 생성(기본 3개, strictness로 조정)해 원 질문 임베딩과의 코사인 유사도를 평균: (1/N) Σ cos(E_gi, E_o). "불완전하거나 불필요한 세부를 담은 답변을 감점"하되 "사실 정확성은 평가하지 않는다". 코사인 범위 때문에 0–1 보장은 없음 ✗ [49]
Noise Sensitivity "관련/무관 검색 문서를 사용할 때 잘못된 응답을 내는 빈도", 낮을수록 좋음. 공식 문서의 약식 수식은 틀린 주장 수 / 전체 주장 수이지만 [50], 구현은 각 주장을 (a) 참조 답안 기준으로 틀렸는지, (b) 어떤 검색 문맥이 뒷받침하는지 둘 다 판정한다. 검색 문맥 중 참조 답안의 주장을 뒷받침하는 것을 "관련 문맥"으로 정하고, mode="relevant" = mean(관련 문맥이 뒷받침 AND 틀림), mode="irrelevant" = mean(무관 문맥만 뒷받침 AND 틀림). 따라서 어느 문맥에도 없는 순수 환각은 세지 않는다(그건 Faithfulness의 몫). 문서 예시: 3개 주장 중 1개가 정답에 없는 내용 → 0.333 ○ (정답 대비 주장 판정) [50]
Factual Correctness / Correctness 응답 vs 참조 답안. Ragas는 FactualCorrectness, LangSmith 튜토리얼은 "RAG 답변이 정답과 얼마나 유사한지" LLM-as-judge로 채점 ○ [56][36]
Semantic Similarity, BLEU/ROUGE 응답과 참조의 임베딩 유사도 / n-gram 중복. Ragas가 "NLP 비교" 범주로 제공 ○ [34]

Faithfulness와 Noise Sensitivity의 차이: Faithfulness는 문맥에 근거했는가(문맥이 틀렸어도 문맥대로 답하면 만점), Noise Sensitivity는 문맥에 근거했지만 정답 기준으로 틀린 주장의 비율을 본다. [35][50] 두 지표 모두 "참조 답안에 없는 내용"과 "현실에서 거짓인 내용"을 구분하지 못하므로, 참조 답안이 불완전하면 옳은 보충 설명이 오류로 집계된다 — 참조 답안 품질이 곧 지표 품질이다.

5.5 도구별 정리

Ragas [33][34] - 논문(arXiv 2309.15217, 2023-09-26 / v2 2025-04-28): 참조 답안 없이(reference-free) RAG 파이프라인을 평가하는 프레임워크. 사람 주석 없이 빠른 평가 사이클이 목표. [33] - RAG 지표: Context Precision, Context Recall, Context Entities Recall, Noise Sensitivity, Response Relevancy, Faithfulness, Multimodal Faithfulness, Multimodal Relevance. 그 외 에이전트/도구 사용, NLP 비교, SQL, rubric 지표. 많은 지표가 LLM 호출로 계산된다. [34] - 공식 시작 가이드 코드(2026-09-13 확인, ragas 0.4 문서 기준). 아래는 dataset(질문·검색 문맥·응답·참조 목록)과 llm(LangChain 챗 모델)이 준비돼 있다고 가정한 발췌다: [56]

from ragas import EvaluationDataset
evaluation_dataset = EvaluationDataset.from_list(dataset)

from ragas import evaluate
from ragas.llms import LangchainLLMWrapper
from ragas.metrics import LLMContextRecall, Faithfulness, FactualCorrectness

evaluator_llm = LangchainLLMWrapper(llm)
result = evaluate(
    dataset=evaluation_dataset,
    metrics=[LLMContextRecall(), Faithfulness(), FactualCorrectness()],
    llm=evaluator_llm
)

{'context_recall': 1.0000, 'faithfulness': 0.8571, 'factual_correctness': 0.7280}

  • 합성 테스트셋 생성: 문서를 청킹해 계층적 노드를 만들고, Extractor(예: NERExtractor)로 노드 속성을 뽑아 Relationship Builder로 노드를 연결한 지식 그래프를 구축한다. 그 위에서 QuerySynthesizer가 노드·질의 길이·스타일·페르소나를 조합해 Single-Hop Specific / Single-Hop Abstract / Multi-Hop Specific / Multi-Hop Abstract 네 유형의 질문을 참조 문맥·답안과 함께 생성한다. [55]

TruLens RAG Triad [52] — Context Relevance / Groundedness / Answer Relevance. Groundedness는 "개별 주장을 나누고 각 주장을 지지하는 근거를 검색 문맥에서 독립적으로 찾는" 방식으로, Ragas Faithfulness와 같은 원리다. [52][35]

ARES(NAACL 2024, arXiv 2311.09476) [54] — context relevance, answer faithfulness, answer relevance 세 차원을 평가하되, LLM-as-judge를 매번 호출하는 대신 합성 학습 데이터로 경량 LM 판정기를 미세조정하고, PPI(prediction-powered inference) 로 수백 개의 사람 주석만으로 판정 오차를 보정한다. 질의·문서 유형이 바뀌는 도메인 이동에도 판정기가 유효했다.

※ Ragas의 검색 지표는 질문이 아니라 답안을 기준으로 청크를 판정한다: LLMContextPrecisionWithReference는 "청크가 참조 답안에 유용한가 + 그 순위", LLMContextPrecisionWithoutReference는 "청크가 생성 응답에 유용한가 + 그 순위", LLM 기반 Context Recall은 "참조 답안의 주장을 문맥이 얼마나 뒷받침하는가"다. 5.7 실무 체크리스트

  1. 검색부터 따로 측정한다. 생성 점수가 낮으면 원인이 검색(Recall 부족, 노이즈)인지 생성(Faithfulness 부족)인지 분리해야 한다. Ragas 논문의 세 차원 분리와 RAG Triad가 이 이유로 존재한다. [33][52]
  2. k와 지표를 프롬프트 예산에 맞춘다. 프롬프트에 5개 청크를 넣는다면 Recall@5·nDCG@5를 본다. Chroma 청킹 연구처럼 "문서 순위보다 LLM 컨텍스트 효율이 중요"하면 토큰 단위 recall/precision/IoU를 쓴다. [46]
  3. 리랭킹·하이브리드 실험은 후보 단계와 최종 선택 단계를 나눠 본다. 후보 N개의 Recall@N(놓쳤는가)과 최종 k개의 nDCG@k·Recall@k(위에 올렸는가)를 함께 측정한다. 순위 지표만 오르고 답변 품질이 그대로면 프롬프트 구성(2.7절)을 의심한다. (5.2절 예시) [51][22]
  4. 참조 없는 지표로 프로덕션 모니터링, 참조 있는 지표로 회귀 테스트. Faithfulness·Response Relevancy는 정답 없이 실시간 계산 가능, Correctness·Context Recall은 데이터셋이 필요하다. [35][49][48][36]
  5. LLM 판정기 비용을 관리한다. 지표 대부분이 LLM 호출이므로 [34], 규모가 크면 ARES처럼 경량 판정기 + 소량 사람 주석으로 보정하는 접근을 고려한다. [54]
  6. 테스트셋은 단일 홉만 넣지 않는다. Ragas 생성기의 Multi-Hop 유형처럼 여러 문서를 합쳐야 답할 수 있는 질문을 포함해야 Advanced RAG(3장)의 효과가 드러난다. [55]

6. 2025–2026 최신 동향

6.1 긴 컨텍스트(Long Context) vs RAG 논쟁

  • Li et al. (EMNLP 2024 Industry, arXiv 2407.16833): 최신 LLM 3종으로 여러 공개 데이터셋에서 RAG와 LC(long-context)를 비교한 결과, "자원이 충분하면 LC가 평균 성능에서 RAG를 일관되게 앞선다". 하지만 RAG의 훨씬 낮은 비용은 뚜렷한 장점이다. 저자들은 모델의 자기 반성으로 질의를 RAG 또는 LC로 라우팅하는 Self-Route를 제안해, LC에 필적하는 성능을 유지하면서 계산 비용을 크게 줄였다. [37]
  • Lost in the Middle (arXiv 2023 / TACL 2024): 관련 정보가 입력의 처음이나 끝에 있을 때 성능이 가장 높고, 긴 문맥의 중간에 있으면 크게 저하되는 U자형 곡선이 관찰됐다. 긴 문맥 전용 모델에서도 이 한계가 지속된다. [38]
  • Anthropic의 실무 지침: 지식 베이스가 20만 토큰 미만이면 RAG 없이 프롬프트 캐싱 + 전체 삽입이 가능하다고 안내한다. [22] 3.3절에서 적었듯 일반 규칙이 아니라 비교 후보로 다룬다.
  • Anthropic Context Engineering(2025-09-29): 문맥이 길어질수록 성능이 저하되는 "context rot" 현상과, 토큰마다 소모되는 "attention budget" 개념을 제시한다. 트랜스포머는 n² 쌍별 토큰 관계를 계산해야 하므로 문맥이 길수록 주의가 얇게 퍼진다. [40]

→ 정리: 긴 컨텍스트가 RAG를 완전히 대체하지는 않는다. 비용, 중간 위치 정보 손실, context rot 때문에 작은 코퍼스는 전체 삽입, 큰 코퍼스는 RAG, 그 사이는 라우팅(Self-Route) 이 현재 근거 있는 절충안이다. [37][38][22][40]

6.2 컨텍스트 엔지니어링(Context Engineering)과 RAG의 재정의

  • LangChain 블로그(2025-07-02): 컨텍스트 엔지니어링은 "에이전트 궤적의 각 단계에서 컨텍스트 윈도우를 딱 맞는 정보로 채우는 기술과 과학". 네 가지 전략 — Write(스크래치패드·메모리로 컨텍스트 밖에 저장), Select(메모리·도구·지식을 필요할 때 가져오기), Compress(요약·트리밍), Isolate(멀티 에이전트·상태 객체로 분리). RAG는 Select 전략의 핵심 과제로 다뤄지며, 코드베이스가 커질수록 "grep/파일 검색, 지식 그래프 기반 검색"에 리랭킹을 결합하는 접근이 언급된다. [39]
  • Anthropic(2025-09-29): 프롬프트 엔지니어링이 "명령을 쓰고 구성하는 것"이라면, 컨텍스트 엔지니어링은 "추론 중 최적의 토큰 집합을 큐레이션·유지하는 전략"으로 시스템 지시, 도구, 외부 데이터, 메시지 이력을 모두 포함한다. 검색에 대해서는 사전 검색(pre-retrieval) 대신 "just-in-time" 컨텍스트 — 에이전트가 파일 경로, 저장된 질의, 링크 같은 경량 식별자를 유지하고 런타임에 도구로 동적으로 데이터를 가져오는 방식 — 이 늘고 있다고 설명한다. 긴 작업에는 compaction(대화 요약 후 새 컨텍스트로 재시작)을 사용한다. [40]
  • LangChain Deep Agents RAG(2026 문서)의 "Retrieve, offload, and delegate" 패턴은 이 원칙의 구현 사례다: 검색 결과를 파일시스템에 내리고 서브에이전트에 위임해 오케스트레이터 컨텍스트를 보호한다. [2]

6.3 MCP(Model Context Protocol)와 RAG

  • Anthropic은 2024-11-25 MCP를 "데이터 소스와 AI 도구 사이에 안전한 양방향 연결을 만들 수 있는 개방형 표준"으로 공개했다. 문제의식은 고도화된 모델이 "정보 사일로와 레거시 시스템에 갇혀 데이터로부터 고립"되어 있고, 새 데이터 소스마다 맞춤 구현이 필요했다는 점이다. 개발자는 MCP 서버로 데이터를 노출하거나 MCP 클라이언트로 AI 앱을 만든다. [41]
  • RAG 관점에서 MCP는 지식 베이스·검색 시스템을 에이전트가 호출하는 표준화된 도구로 노출하는 수단이다. LangChain 문서가 말하듯 Agentic RAG는 "외부 지식을 가져올 수 있는 도구 하나 이상"만 있으면 성립하므로 [3], MCP 서버로 감싼 검색 시스템은 곧 Agentic RAG의 도구가 된다. (이 문장은 [3]과 [41]의 정의를 결합한 해석이며, 두 문서가 서로를 직접 언급하지는 않는다.)

6.4 매니지드 RAG (Managed Retrieval)

  • OpenAI Retrieval API: 벡터 스토어에 파일을 추가하면 "자동으로 청킹·임베딩·인덱싱"된다. 기본 800토큰 청크, 400토큰 오버랩(조정 가능). 하이브리드 검색 가중치(hybrid_search.embedding_weight / text_weight, RRF 기반), 리랭킹(ranking_options, score threshold 0.0–1.0), 질의 자동 재작성(rewrite_query=true)을 제공한다. [45]
  • 시사점: 청킹·하이브리드·리랭킹·쿼리 재작성이 API 한 줄의 옵션이 될 만큼 표준 스택이 됐다. 그러나 2.2절의 Chroma 연구가 보여주듯 청크 크기·전략은 여전히 성능에 큰 영향을 주므로 기본값을 검증 없이 쓰면 안 된다. [46]

6.5 멀티모달 RAG

  • ColPali(ICLR 2025): 문서는 텍스트뿐 아니라 그림, 페이지 레이아웃, 표, 폰트로 정보를 전달하는데, 기존 검색은 "길고 취약한" 텍스트 추출 과정에 의존해 시각 단서를 활용하지 못한다. ColPali는 페이지 이미지에서 직접 다중 벡터 임베딩을 만든다. 모델·데이터셋·코드가 Hugging Face에 공개됐다. [42]
  • 평가: Ragas는 Multimodal Faithfulness, Multimodal Relevance 지표로 텍스트 + 이미지 문맥에 대한 응답의 충실성·관련성을 평가한다. 지표 문서가 명시한 입력은 문자열, 이미지 URL, 로컬 이미지 경로(jpg/png/gif/webp/bmp), base64 이미지이며 비디오는 포함되지 않는다. [34]

6.6 프로덕션 관점 — 비용, 지연, 보안

비용·지연 - RAG의 낮은 비용은 LC 대비 뚜렷한 장점이며, Self-Route 같은 라우팅으로 비용을 더 줄일 수 있다. [37] - Contextual Retrieval의 문맥 생성은 프롬프트 캐싱으로 약 $1.02/100만 문서 토큰. [22] - 임베딩 비용: OpenAI text-embedding-3-small은 large보다 pages-per-dollar가 약 6.5배 높다(62,500 vs 9,615). dimensions 축소로 저장·검색 비용도 절감 가능. [7] - Agentic RAG는 유연성이 높은 대신 지연 시간이 가변적이다. [3] - ColBERT류 late interaction은 문서 표현을 오프라인 계산해 온라인 지연을 줄인다. [15]

보안 — 프롬프트 인젝션과 벡터 스토어 취약점 - LangChain RAG 문서의 경고: "RAG 애플리케이션은 간접 프롬프트 인젝션(indirect prompt injection) 에 취약하다. 검색된 문서에 명령처럼 보이는 텍스트가 포함될 수 있다." [2] - OWASP LLM01:2025 Prompt Injection: "사용자 프롬프트가 LLM의 동작이나 출력을 의도치 않은 방식으로 바꿀 때 발생". 간접 인젝션은 LLM이 웹사이트·파일 등 외부 소스의 입력을 받을 때 발생한다. "RAG와 fine-tuning은 출력의 관련성·정확성을 높이려 하지만, 연구에 따르면 프롬프트 인젝션 취약점을 완전히 완화하지는 못한다." 예시 시나리오: 공격자가 RAG 앱이 쓰는 저장소의 문서를 수정하고, 사용자의 질의가 그 악성 내용을 검색하면 주입된 지시가 LLM 출력을 바꾼다. [43] - OWASP LLM08:2025 Vector and Embedding Weaknesses: "벡터와 임베딩 취약점은 RAG를 사용하는 LLM 시스템에 상당한 보안 위험을 초래한다." 위험 유형: (1) 접근 통제 미흡으로 인한 무단 접근·데이터 유출, (2) 멀티테넌트 환경의 교차 컨텍스트 정보 누출, (3) 임베딩에서 원문을 복원하는 임베딩 역전(embedding inversion) 공격, (4) 데이터 포이즈닝, (5) RAG가 모델의 기초 특성(예: 공감 능력)을 바꾸는 행동 변화. 예방책: 세밀한 접근 통제와 권한 인식(permission-aware) 벡터 스토어, 신뢰된 소스 검증과 지식 베이스 정기 감사, 데이터 분류, 검색 활동의 불변 로그 유지. [44]

8. 정리 — 한 장 요약

  1. RAG = 파라메트릭 메모리(LLM) + 비파라메트릭 메모리(외부 인덱스). 환각, 지식 갱신, 출처 제시 문제에 대한 답으로 2020년 등장. [1]
  2. 기본 파이프라인은 Load → Split → Embed → Store → Retrieve → Generate. 청킹 전략과 크기가 성능에 큰 영향을 준다. [2][46]
  3. 검색은 dense + sparse 하이브리드(RRF)에 리랭킹을 얹는 것이 표준이 됐다. [12][14][22][45]
  4. Advanced RAG는 "무엇을 검색할지"(쿼리 변환), "무엇을 인덱싱할지"(부모-자식, Contextual, Late Chunking, GraphRAG), "검색 결과를 믿을지"(Self-RAG, CRAG, Adaptive)로 나뉜다. [16]–[27]
  5. Agentic RAG는 검색을 에이전트의 도구로 만들고, 채점·재작성·재검색 루프를 LangGraph로 구현한다. [3][29]
  6. 평가는 검색(Precision/Recall@k, MRR, MAP, nDCG, Context Precision/Recall)과 생성(Faithfulness, Response Relevancy, Correctness)을 분리해 측정한다. 검색 ↔ 질문, 응답 ↔ 문맥, 응답 ↔ 질문의 세 관계(RAG Triad)가 골격이다. [51][34][36][52]
  7. 2025–2026의 핵심 질문은 "RAG냐 긴 컨텍스트냐"가 아니라 컨텍스트 엔지니어링 — 언제, 무엇을, 얼마나 컨텍스트에 넣을지 — 이며, 간접 프롬프트 인젝션과 벡터 스토어 보안이 프로덕션 필수 과제다. [37][39][40][43][44]
